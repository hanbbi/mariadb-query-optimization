# 측정 방법과 결과

이 저장소는 실무에서 수행한 쿼리 최적화를, 회사 데이터 없이 로컬 더미 데이터로
재현할 수 있게 구성한 것입니다. 측정은 실행계획 예측(`EXPLAIN`)이 아니라
실제 실행 통계(`ANALYZE FORMAT=JSON`)로 하며, 두 값을 근거로 삼습니다.

- `r_rows` : 실제로 읽은 행 수
- `r_total_time_ms` : 실제 소요 시간(ms)

## 단계별로 확인되는 변화

`sql/02_queries.sql`을 STAGE 순서대로 실행하면, 같은 "월별 단말기 사용량 합계"
조회가 아래처럼 바뀝니다.

- **STAGE 0 → 1**: 조건만 sargable(범위 조건)로 교체. 인덱스가 없어 여전히 풀 스캔이라
  시간은 거의 줄지 않음 — "함수라서 느린 것"이 아니라 "인덱스를 못 타는 것"이 본질임을 확인.
- **STAGE 1 → 2**: 복합·커버링 인덱스 적용. range scan으로 읽는 행이 급감하고,
  집계에 필요한 값이 인덱스에 다 있어 테이블 룩업도 사라짐(커버링).
- **STAGE 2 → 3**: 자주 불리는 대시보드 조회는 매번 한 달치를 재집계하는 대신,
  트리거+배치로 유지되는 요약 테이블(수백 행)만 읽음.

읽는 행 수가 수천만 → 수백만(range·커버링) → 수백(요약 테이블)으로 줄면서
소요 시간도 같은 방향으로 급감합니다.

> 참고: 이력서에 적힌 "약 10초 → 약 2초"는 실무 운영 환경(약 5천만 행, 운영 서버)에서
> 측정한 값입니다. 로컬 재현 환경은 하드웨어·데이터 규모가 달라 절대 시간은 다를 수 있으나,
> 단계별로 줄어드는 패턴은 동일하게 나타납니다.
